L'historique de Delta, le restore et le drop 4

Leçon 7 · jeudi 13h15 · Demander à une table ce qu'un hop a fait, annuler un mauvais run, et choisir d'accepter un changement de schema

Pourquoi cette leçon Toute vraie plateforme finit par poser deux questions, en général au pire moment : « qu'est-ce que le run de cette nuit a changé ? » et « on peut revenir en arrière ? ». Le log de Delta répond aux deux. Ensuite le drop 4 arrive avec les colonnes renommées et nouvelles de la war story de la leçon 2. Et cette fois, tu les acceptes parce que tu l'as décidé.

1. Le log, c'est la mémoire de la table

Chaque écriture réussie est un commit avec une version, une opération et des métriques (table utility commands). Pour un MERGE :

h = DeltaTable.forPath(spark, silver).history()
h.select("version", "operation",
         F.col("operationMetrics.numTargetRowsInserted").alias("ins"),
         F.col("operationMetrics.numTargetRowsUpdated").alias("upd")).orderBy("version").show()

Voici le silver après l'avoir construit deux fois depuis le même bronze. L'historique va du plus récent au plus ancien, c'est pour ça que tu ajoutes orderBy :

versionoperationinsupdLecture
0WRITENULLNULLtable vide de ton premier run
1MERGE60premier chargement : six codes-barres, tous nouveaux
2MERGE00re-run, même bronze : rien n'a changé

Pour revenir en arrière dans le log :

  • spark.read.format("delta").option("versionAsOf", n) lit la table telle qu'elle était à la version n.
  • DeltaTable.forPath(spark, path).restoreToVersion(n) rend la version n courante à nouveau, sous la forme d'un nouveau commit (RESTORE dans l'historique). Rien n'est effacé.

2. Exercice : casse-la, regarde, restaure core

En local, dans jobs/explore_history.py, construis le silver avec tes propres split et merge_silver à partir de quatre ou cinq lignes bronze. Ensuite simule un mauvais run, causé par un mauvais mode :

v_good = DeltaTable.forPath(spark, silver).history(1).first().version
spark.read.format("delta").load(silver).limit(1) \
     .write.format("delta").mode("overwrite").save(silver)        # the bad run

Écris ta prédiction pour chaque étape, puis affiche :

  1. le nombre de lignes actuel
  2. le nombre de lignes à versionAsOf = v_good
  3. les trois dernières entrées de l'historique (version, operation)
  4. après restoreToVersion(v_good) : le nombre de lignes, et la dernière opération.

C'est bon quand le compte restauré est égal au compte à v_good, que l'historique se termine par RESTORE, et que tu sais expliquer pourquoi la mauvaise version est toujours lisible.

Le restore a une limite Le time travel et le restore ont besoin des anciens fichiers de données. Une fois que VACUUM a supprimé les fichiers non référencés au-delà de la rétention (7 jours par défaut), ces versions sont perdues (utility commands: vacuum). Personne ne lance VACUUM cette semaine. Sur une plateforme client, demande qui le fait, et quand.

3. Drop 4 : prédis d'abord

Le header du drop 4 renomme sugars_100g en sugar_100g et ajoute ecoscore_grade. Ton job bronze append tout ce qu'il lit. Qu'est-ce qui se passe ? Écris-le, puis relis le geste 5 de la leçon 2.

Ce qui se passe — à ouvrir après ta prédiction

Le batch plante : A schema mismatch detected when writing to the Delta table. Le bronze refuse les deux colonnes inconnues, sugar_100g et ecoscore_grade, et n'écrit rien. Cette erreur, c'est le garde-fou que la plateforme de la war story de la leçon 2 avait désactivé.

Le garde-fou rate un cas. Un drop à qui il manque juste une colonne passe, avec cette colonne à null sur toutes les lignes. Si le fournisseur avait supprimé sugars_100g, le bronze l'aurait chargé sans erreur, et le silver aurait perdu le sucre. Les colonnes manquantes, c'est le boulot de ton contract et de tes comptes par règle.

4. Exercice : accepter le changement, en connaissance de cause core

Deux décisions, chacune sur une ligne qu'un reviewer peut lire dans ta PR :

from delta import DeltaTable

RENAMES = {"sugar_100g": "sugars_100g"}   # drop 4: the supplier renamed a column
ADDED = {"ecoscore_grade": "STRING"}      # drop 4: a new column, accepted on purpose


def load_bronze(spark, landing, bronze):
    raw = spark.read.option("header", True).csv(landing).withColumnsRenamed(RENAMES)
    if DeltaTable.isDeltaTable(spark, bronze):
        have = set(spark.read.format("delta").load(bronze).columns)
        for name, sql_type in ADDED.items():
            if name in raw.columns and name not in have:
                spark.sql(f"ALTER TABLE delta.`{bronze}` ADD COLUMNS ({name} {sql_type})")
    ...  # stamp and append, unchanged

withColumnsRenamed ignore les noms absents, du coup les anciens drops passent sans changement (API). ALTER TABLE … ADD COLUMNS fait son propre commit : l'historique montre la décision, et les anciennes lignes se lisent à null (batch writes: update table schema). Écris les deux tests d'abord :

def test_drop4_rename_and_new_column(spark, tmp_path):
    for n, body in [("drop1", "code,sugars_100g\n001,45\n"),
                    ("drop4", "code,sugar_100g,ecoscore_grade\n002,4,a\n")]:
        (tmp_path / n).mkdir(); (tmp_path / n / "p.csv").write_text(body)
        load_bronze(spark, str(tmp_path / n), str(tmp_path / "bronze"))
    b = spark.read.format("delta").load(str(tmp_path / "bronze"))
    assert sorted((r.code, r.sugars_100g, r.ecoscore_grade) for r in b.collect()) == [
        ("001", "45", None), ("002", "4", "a")]


def test_unknown_new_column_is_refused(spark, tmp_path):
    import pytest
    for n, body in [("d1", "code\n001\n"), ("d2", "code,surprise\n002,x\n")]:
        (tmp_path / n).mkdir(); (tmp_path / n / "p.csv").write_text(body)
    load_bronze(spark, str(tmp_path / "d1"), str(tmp_path / "bronze"))
    with pytest.raises(Exception, match="schema mismatch"):
        load_bronze(spark, str(tmp_path / "d2"), str(tmp_path / "bronze"))

Le deuxième test protège le garde-fou : la prochaine colonne surprise plante toujours. Ensuite charge le drop 4 dans le bronze et relance le silver et le gold. Un piège : le silver écrase la quarantine, et les lignes rejetées portent maintenant ecoscore_grade, donc le même garde-fou refuse cette écriture. La quarantine est reconstruite à chaque run, alors laisse son schéma suivre le bronze : ajoute .option("overwriteSchema", "true") à l'écriture de la quarantine. Lis chaque batch avec gcloud dataproc batches wait (leçon 3, section 3), le dernier Traceback d'abord si ça a échoué. ecoscore_grade reste hors du silver tant que personne n'a décidé de l'y mettre.

C'est bon quand les deux tests passent, que le drop 4 est dans le bronze, et que l'historique du bronze montre ADD COLUMNS. drop next vérifie le drop 4 et te donne le drop 5, le capstone de vendredi. Le commencer ou pas, c'est toi qui vois.

Refusé deux fois avec la même ligne ? Poste-la sur Teams avec ton handle, puis drop next --force et dis-le dans ta PR (leçon 3, section 4).

5. Stretch : quelles lignes ont changé stretch

Pour voir quelles lignes ont changé, et pas combien, fais un diff des deux dernières versions du silver : affiche new.exceptAll(old) et old.exceptAll(new) (exceptAll). Ajoute-le à la sortie du batch silver après le MERGE, limité à 20 lignes. Sur une plateforme client, c'est le snippet à coller dans le canal d'incident.
