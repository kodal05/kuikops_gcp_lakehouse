DataFrames et Delta, en local

Leçon 2 · mardi 9h45 · Lire un fichier, le tamponner, l'ajouter à Delta, et voir Delta en refuser un mauvais

≈ 60 minutesPrérequis : leçon 1, le drop 1 dans ton landingRéférence : glossaire (en anglais) · cheat sheet (en anglais)
Pourquoi cette leçon Le batch landing→bronze de cet après-midi, c'est cinq gestes : lire, tamponner, ajouter (append), relire, et se faire refuser. Entraîne-toi ici, en local, sur deux tout petits fichiers. Le bronze, c'est le hop le plus simple, mais une erreur là-dedans fait le plus mal : toutes les couches suivantes lui font confiance. Sur un projet client, c'est une équipe source que tu ne contrôles pas qui alimente le bronze. Du coup, une écriture refusée est souvent le premier signe qu'elle a changé quelque chose.

1. Une session, deux configs

Delta, c'est un format de table : des fichiers Parquet plus un journal de transactions. Spark a besoin de deux réglages pour ça (quick start), déjà dans une fixture de scope session dans le tests/conftest.py du template :

from delta import configure_spark_with_delta_pip
from pyspark.sql import SparkSession

builder = (SparkSession.builder.master("local[2]")
  .config("spark.sql.extensions", "io.delta.sql.DeltaSparkSessionExtension")
  .config("spark.sql.catalog.spark_catalog", "org.apache.spark.sql.delta.catalog.DeltaCatalog"))
spark = configure_spark_with_delta_pip(builder).getOrCreate()

Sur le runtime des batches, garde les deux lignes .config mais saute configure_spark_with_delta_pip : Delta est déjà sur le classpath (regarde le hello.py de la leçon 1).

2. Les cinq gestes core

Enregistre-le sous learners/<handle>/jobs/explore.py, lance-le avec uv run python -m jobs.explore. Avant de le lancer, note ce que vont afficher les quatre lignes print numérotées. Ensuite, compare.

import tempfile, os
from pyspark.sql import functions as F
from tests.conftest import make_spark        # same builder as the fixture
spark = make_spark()

d = tempfile.mkdtemp(); landing = f"{d}/landing"; bronze = f"{d}/bronze"
os.makedirs(landing)
open(f"{landing}/drop1.csv", "w").write("code,product_name,sugars_100g,last_modified\n001,Choco,45,2026-01-01\n002,Water,0,2026-01-01\n")
open(f"{landing}/drop2.csv", "w").write("code,product_name,sugars_100g,last_modified\n001,Choco bar,44,2026-02-01\n,NoBarcode,1,2026-02-01\n003,Juice,10,2026-02-01\n")

# move 1: read. Every column is a string; bronze keeps it that way.
raw = spark.read.option("header", True).csv(landing)

# move 2: stamp. Which file, when.
stamped = raw.select("*",
    F.col("_metadata.file_path").alias("source_file"),
    F.current_timestamp().alias("loaded_at"))

# move 3: append.
stamped.write.format("delta").mode("append").save(bronze)

# move 4: read back.
b = spark.read.format("delta").load(bronze)
print("1. rows:", b.count())
print("2. distinct source files:", b.select("source_file").distinct().count())
print("3. sugars type:", dict(b.dtypes)["sugars_100g"])

# move 5: be refused. A drop with a new column.
try:
    stamped.withColumn("extra", F.lit(1)).write.format("delta").mode("append").save(bronze)
    print("4. appended")
except Exception as e:
    print("4. refused:", str(e).splitlines()[0][:80])

C'est bon quand tu as écrit quatre prédictions, lancé le script, et comparé chacune à la section 3.

3. Ce que tu viens de voir

LigneValeurPourquoi
15Deux fichiers, cinq lignes. Le bronze fait de l'append, donc le doublon 001 fait deux lignes, et c'est normal.
22Le fichier de chaque ligne. _metadata.file_path remplace input_file_name() (file metadata column).
3stringLe CSV donne des strings, et le bronze ne caste pas. Le typage, c'est le job du silver, et son risque.
4refused: A schema mismatch detected…Schema enforcement : toute l'écriture échoue, rien de partiel n'atterrit (batch writes: schema validation).
La galère de lundi : pourquoi le bronze refuse les nouvelles colonnes La ligne 4, c'est pour ça que tu peux faire confiance au bronze. L'option mergeSchema, ou le réglage de session spark.databricks.delta.schema.autoMerge.enabled, transforme le refus en nouvelle colonne, sans aucune erreur. La doc Delta dit d'autoMerge qu'il est « not recommended because it can lead to unintended schema changes ». Une vraie plateforme tournait avec autoMerge activé : une colonne renommée par le fournisseur est devenue une nouvelle colonne nulle, sans aucune erreur. Le drop 4 va te tenter : une nouvelle colonne, c'est une décision, pas un réglage par défaut.

4. Exercice : l'historique core

Ajoute ces lignes à explore.py et prédis la sortie avant de lancer :

from delta import DeltaTable
print("5.", [(r.version, r.operation) for r in DeltaTable.forPath(spark, bronze).history().select("version", "operation").collect()])
print("6.", spark.read.format("delta").option("versionAsOf", 0).load(bronze).count())

C'est bon quand tu sais dire, sans regarder, combien il y a de versions et pourquoi l'écriture refusée n'en est pas une (table utility commands).

5. Stretch : le cast qui mord stretch

Le drop 3 va livrer des quantités comme "12 g". Lance spark.createDataFrame([("12 g",)], ["q"]).select(F.col("q").cast("double")).show() en local. Ça lève une erreur au lieu de renvoyer null : l'ANSI mode est activé par défaut (migration guide).

  1. Trouve la fonction de pyspark.sql.functions qui renvoie null à la place.
  2. Note quelle couche devrait l'utiliser.
  3. Note ce qui devrait arriver à la ligne devenue null.
