Tes buckets et ton premier batch

Leçon 1 · lundi 14h15 · Déclarer les quatre couches en Terraform, lancer un batch Spark, recevoir le drop 1

≈ 90 minutesPrérequis : leçon 0 au vert, PR de setup mergéeRéférence : glossaire (en anglais) · cheat sheet Terraform & gcloud (en anglais)
Pourquoi cette leçon Le pipeline de la semaine vit dans quatre buckets et tourne en batches. Comme tout est déclaré en code, ta plateforme entière tient dans un dossier que quelqu'un d'autre pourrait apply vendredi. Le batch hello d'aujourd'hui sert juste à prouver le chemin de ton laptop jusqu'à un batch sur GCS. Du coup, le job de demain ne parle que du bronze.

1. La boucle de Terraform : déclarer, plan, apply, state

Terraform, c'est une boucle :

  1. Tu déclares des ressources dans des fichiers .tf.
  2. terraform plan montre la différence entre ces fichiers et ce qui existe.
  3. terraform apply l'applique, et le fichier de state se souvient de ce qu'il a fait.

Ton state vit dans le bucket de state partagé, avec ton handle en préfixe. Comme ça, dix apprenants ne s'écrasent pas les uns les autres (Terraform docs: GCS backend). Sandbox : le formateur a créé ce bucket de state et le backend.tf du template pour toi. Sur un projet client, toi ou leur équipe plateforme créez et verrouillez le bucket de state avant le premier init.

# learners/<handle>/terraform/backend.tf  (already in the template)
terraform {
  backend "gcs" {
    bucket = "kuikops-lakehouse-tfstate"
    # prefix comes from the command line so the file is identical for everyone
  }
}
cd learners/<handle>/terraform
terraform init -backend-config="prefix=<handle>"
terraform plan
Lis le plan avant de taper yes Si plan veut détruire quoi que ce soit, ou affiche le handle de quelqu'un d'autre, ton préfixe est faux. N'applique pas, corrige le init.

2. Exercice : quatre buckets core

Déclare un bucket par couche : landing, bronze, silver, gold (la quarantine vit dans le bucket silver). Les noms de bucket sont globaux, du coup ils contiennent l'id du projet et ton handle. Utilise google_storage_bucket avec juste les deux options ci-dessous.

resource "google_storage_bucket" "landing" {
  name                        = "${var.project_id}-${var.handle}-landing"
  location                    = "europe-west1"
  uniform_bucket_level_access = true   # IAM on the bucket, no per-object ACLs
  force_destroy               = true   # sandbox: destroy may delete objects
}

C'est bon quand terraform apply annonce quatre ajouts et que cette commande liste tes quatre buckets :

for l in landing bronze silver gold; do gcloud storage buckets describe gs://kuikops-lakehouse-<handle>-$l --format="value(name)"; done

3. Exercice : un batch qui prouve le runtime core

Un batch, c'est un run d'un job sur Serverless for Apache Spark. Tu soumets un fichier, et Google le lance, facture les secondes et s'arrête (overview). Le runtime a déjà Spark, Python et Delta, du coup tu n'envoies que ton script (runtime versions).

Deux ressources, dans l'ordre : mets le script dans un bucket (google_storage_bucket_object), puis déclare le batch (google_dataproc_batch). Le template fournit jobs/hello.py :

# jobs/hello.py: write three rows to Delta in your bronze bucket, read them back
import sys
from pyspark.sql import SparkSession

bronze = sys.argv[1]
spark = (SparkSession.builder.appName("hello")
         .config("spark.sql.extensions", "io.delta.sql.DeltaSparkSessionExtension")
         .config("spark.sql.catalog.spark_catalog", "org.apache.spark.sql.delta.catalog.DeltaCatalog")
         .getOrCreate())
df = spark.createDataFrame([(1, "landing"), (2, "bronze"), (3, "silver")], ["n", "layer"])
df.write.format("delta").mode("overwrite").save(f"{bronze}/hello")
print("rows:", spark.read.format("delta").load(f"{bronze}/hello").count())

Fais l'apply en deux fois. D'abord, ajoute seulement google_storage_bucket_object.hello, fais un apply, et vérifie que le script est bien là : gcloud storage ls gs://…-landing/jobs/. Ensuite, ajoute le batch en dessous et refais un apply.

resource "google_storage_bucket_object" "hello" {
  bucket = google_storage_bucket.landing.name
  name   = "jobs/hello.py"
  source = "${path.module}/../jobs/hello.py"
}

resource "google_dataproc_batch" "hello" {
  batch_id = "${var.handle}-hello-${var.run}"
  location = "europe-west1"
  runtime_config {
    version    = "3.0"
    properties = { "spark.dynamicAllocation.maxExecutors" = "2" } # drops are KBs: never scale up
  }
  environment_config {
    execution_config {
      service_account = var.service_account
      ttl             = "1800s" # a hung batch is killed after 30 min
      authentication_config {
        user_workload_authentication_type = "SERVICE_ACCOUNT" # the API sets this: declare it or every apply replaces the batch
      }
    }
  }
  pyspark_batch {
    main_python_file_uri = "gs://${google_storage_bucket_object.hello.bucket}/${google_storage_bucket_object.hello.name}"
    args                 = ["gs://${google_storage_bucket.bronze.name}"]
  }
}

C'est bon quand le batch affiche SUCCEEDED et que son log finit par rows: 3 :

terraform apply -var="run=1"
gcloud dataproc batches list --region=europe-west1 | grep <handle>
gcloud dataproc batches describe <handle>-hello-1 --region=europe-west1 --format="value(state)"

Ensuite, passe run à 2 et refais un apply. Terraform crée un batch, il ne le met pas à jour : les runs sont immuables, d'où le numéro de run dans batch_id.

4. Exercice : drop 1 core

Tu récupères chaque drop quand tu es prêt, peu importe le jour. Le drop 1 est ouvert à tous :

drop next
gcloud storage ls gs://kuikops-lakehouse-<handle>-landing/drop1/

C'est bon quand tu sais citer les fichiers de drop1/ et que tu en as ouvert un avec gcloud storage cat … | head. Ne transforme rien : le seul lecteur de landing, c'est le job de demain.

5. La PR core

  1. Crée la branche <handle>/terraform-buckets.
  2. Commite terraform/ et jobs/hello.py.
  3. Ouvre la PR avec le template et demande une review à ton binôme.
  4. Dans la description de la PR, écris une phrase avec tes mots sur pourquoi run = 2 a créé un nouveau batch au lieu de mettre à jour <handle>-hello-1. Ton binôme la lit avant d'approuver.
  5. La CI lance terraform validate. CI au vert plus une approbation, et c'est mergé.

Ne commite jamais .terraform/ ni un fichier de state. Le .gitignore du template les exclut, mais vérifie que c'est toujours le cas.

6. Stretch : te retrouver dans la facture stretch

Ajoute labels = { owner = var.handle, layer = "landing" } à chaque bucket et fais un apply. Retrouve-les dans Billing → Reports, groupés par label. Les batches sont facturés à la seconde en Data Compute Units, avec une minute minimum (pricing). Ton batch hello a coûté moins qu'un café, et maintenant tu peux le prouver.
