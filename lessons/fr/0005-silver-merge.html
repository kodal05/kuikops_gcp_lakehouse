Silver : MERGE sur la business key

Leçon 5 · mercredi 13h15 · Une ligne par code-barres, la version la plus récente gagne, et un re-run ne change rien

≈ 3 heuresPrérequis : leçon 4 (split qui passe)Référence : PySpark & Delta cheat sheet (en anglais) · glossaire (en anglais)
Pourquoi cette leçon « Une ligne par entité métier », c'est la phrase sur laquelle un client va te tenir. Le bronze a le même code-barres plusieurs fois :
  • des doublons dans un même drop
  • le même produit qui revient dans un drop suivant
  • parfois une version plus ancienne qui arrive après une plus récente
Cet après-midi, le silver garde une ligne par code, celle avec le last_modified le plus récent. Peu importe l'ordre des drops et le nombre de runs.

1. Le MERGE en une image

Un MERGE Delta joint une source (les nouvelles lignes) à une cible (la table) sur une condition. Il gère les lignes qui matchent et celles qui ne matchent pas dans un seul commit atomique (Delta: table deletes, updates and merges) :

from delta import DeltaTable

(DeltaTable.forPath(spark, silver).alias("t")
    .merge(source.alias("s"), "t.code = s.code")       # the business key
    .whenMatchedUpdateAll()                               # same barcode: overwrite the row
    .whenNotMatchedInsertAll()                            # new barcode: insert it
    .execute())

2. Prédis, puis lance : deux pièges

Dans un script de brouillon, crée une table Delta vide (code, n) et une source de deux lignes, ("001","a") et ("001","b"). Tu vas lancer le MERGE ci-dessus deux fois. Note d'abord : combien de lignes après le premier run ? Et après le deuxième ?

Ce qu'on a vu — à ouvrir une fois que tu l'as lancé

Premier run : 2 lignes, toutes les deux en 001. Aucune ligne de la cible n'a matché, donc les deux sont entrées, sans aucune erreur. Deuxième run : [DELTA_MULTIPLE_SOURCE_ROW_MATCHING_TARGET_ROW_IN_MERGE] Cannot perform Merge as multiple source rows matched…. L'erreur ne sort qu'une fois que la cible a la clé.

Deuxième piège : une ligne avec code = null. En SQL, null = null n'est pas vrai. Elle ne matche donc jamais et se fait réinsérer à chaque run. C'est pour ça que code_missing tourne dans split, avant le MERGE.

3. Deux fixes, deux lignes chacun

Rendre la source unique. Garde une ligne par code : le last_modified le plus récent, puis le chargement le plus récent en cas d'égalité. Une window fait ça (row_number) :

SILVER_COLUMNS = ["code", "product_name", "brands", "categories", "countries", "nutrition_grade_fr", "sugars_100g", "last_modified"]   # lesson 4's good, minus loaded_at
from pyspark.sql import Window

w = Window.partitionBy("code").orderBy(F.desc("last_modified"), F.desc("loaded_at"))
latest = good.withColumn("_n", F.row_number().over(w)).filter("_n = 1").select(*SILVER_COLUMNS)

Ne jamais laisser gagner une ligne plus ancienne. Une mise à jour en retard est plus vieille que la ligne du silver. Du coup, on ne met à jour que si la source est plus récente.

.whenMatchedUpdateAll(condition="s.last_modified > t.last_modified")
Idempotent Avec les deux fixes, un re-run sur le même bronze ne change aucune ligne : chaque match rate la condition > et rien n'est inséré. C'est pour ça qu'un batch planté ou relancé ne fait pas de dégâts. Sur un projet client, un orchestrateur relance un run de nuit planté sans te demander, et c'est ça qui rend ce retry sans risque. Ton binôme teste ça en premier dans ta PR. (Delta commit quand même une nouvelle version à chaque run.)

4. Exercice : merge_silver core

Ajoute latest(good) et merge_silver(spark, good, silver) dans jobs/silver.py, et ce test dans tests/test_silver.py (chargement, mise à jour en retard, re-run, mêmes lignes à chaque fois) :

from jobs.silver import split, merge_silver


def silver_rows(spark, path):
    return sorted((r.code, r.product_name, r.last_modified)
                  for r in spark.read.format("delta").load(path).collect())


def test_latest_last_modified_wins_and_rerun_changes_nothing(spark, tmp_path):
    path = str(tmp_path / "silver")
    good, _ = split(bronze(spark,
        ("001", "Choco",     "45", "2026-01-01"),
        ("001", "Choco bar", "44", "2026-02-01"),   # newer: wins
        ("001", "Choco bar", "44", "2026-02-01"),   # exact duplicate
        ("002", "Water",     "0",  "2026-01-01")))
    merge_silver(spark, good, path)
    late, _ = split(bronze(spark, ("002", "Old water", "0", "2025-12-01")))   # late update: older
    merge_silver(spark, late, path)
    want = [("001", "Choco bar", dt.date(2026, 2, 1)), ("002", "Water", dt.date(2026, 1, 1))]
    assert silver_rows(spark, path) == want
    merge_silver(spark, good, path)
    assert silver_rows(spark, path) == want

Au premier run, il n'y a pas de table dans laquelle merger. Crée-la donc vide : if not DeltaTable.isDeltaTable(spark, silver): latest(good).limit(0).write.format("delta").save(silver) (DeltaTable API).

C'est bon quand les deux tests silver passent.

6. Stretch : le prouver avec l'historique stretch

Après un re-run, DeltaTable.forPath(spark, silver).history(1).select("operationMetrics").first()[0] montre ce que le MERGE a fait. Affiche numTargetRowsInserted et numTargetRowsUpdated dans la sortie du batch (table utility commands: history). Lance le silver deux fois sur le même bronze : les deux sont à 0 la deuxième fois. Là, tu peux prouver que c'est idempotent avec un chiffre tiré du log.
