Les règles du silver et la quarantine

Leçon 4 · mercredi 9h45 · Typer chaque colonne, nommer chaque rejet, ne perdre aucune ligne

≈ 2 heuresPrérequis : leçon 3, le drop 2 dans le bronzeRéférence : PySpark & Delta cheat sheet (en anglais) · glossaire (en anglais)
Pourquoi cette leçon Vendredi, un contrat vérifie le silver : des colonnes typées, un code-barres et une date valide sur chaque ligne. Aujourd'hui tu écris la moitié du silver qui rend ça possible. Elle type les strings du bronze, puis coupe les lignes en deux : celles que le silver garde, et celles qu'il refuse, chacune étiquetée avec sa règle. Le MERGE de cet après-midi ne voit que le bon côté.

1. Prédis, puis lance

Le bronze, c'est que des strings. Le silver caste. Et un cast qui ne peut pas réussir lève une erreur au lieu de renvoyer null : l'ANSI mode est activé par défaut (migration guide). Prédis le résultat de chaque ligne, puis lance-la dans une session locale avec spark.sql(f"SELECT {e}").first()[0] :

ExpressionTa prédiction
cast('12 g' AS double)
try_cast('12 g' AS double)
to_date('15/03/2026', 'yyyy-MM-dd')
try_to_timestamp('15/03/2026', 'yyyy-MM-dd')
Ce qu'on a vu — à ouvrir une fois que tu les as lancées

La ligne 1 lève [CAST_INVALID_INPUT] The value '12 g' of the type "STRING" cannot be cast to "DOUBLE" because it is malformed. La ligne 3 lève [CANNOT_PARSE_TIMESTAMP]. Les lignes 2 et 4 renvoient None.

Du coup, avec les lignes 1 et 3, une seule mauvaise ligne tue tout le batch. Avec les formes try_, la ligne survit sous forme de null qu'une règle peut attraper. C'est pour ça que le silver n'utilise que celles-là (pyspark.sql.functions : try_to_timestamp, et try_cast via F.expr).

2. Une seule colonne de règle

Une règle, c'est une condition plus un nom, enchaînés dans un seul F.when. La colonne rule d'une ligne contient la première règle qu'elle rate, ou null si elle n'en rate aucune. Du coup, filtrer sur cette seule colonne te donne les deux côtés, et aucune ligne ne tombe entre les deux.

sugars   = F.expr("try_cast(sugars_100g AS double)")
modified = F.to_date(F.try_to_timestamp("last_modified", F.lit("yyyy-MM-dd")))
typed = bronze_df.withColumns({"_sugars": sugars, "_modified": modified})

rule = (F.when(F.col("code").isNull() | (F.trim("code") == ""), "code_missing")
         .when(F.col("_modified").isNull(), "last_modified_unparseable")
         .when(F.col("sugars_100g").isNotNull() & F.col("_sugars").isNull(), "sugars_not_a_number"))
judged = typed.withColumn("rule", rule)

Regarde bien la troisième règle. Un sucre absent, c'est une inconnue, pas une erreur. Le silver le garde donc en null. Un sucre qui était là mais qu'on n'a pas pu lire, ça c'est une erreur. C'est le isNotNull() sur la colonne du bronze qui fait la différence.

Ce que contient la quarantine La ligne rejetée telle que le bronze l'avait (que des strings, avec source_file et loaded_at), plus rule et rejected_at. La personne qui demande au fournisseur « pourquoi cette ligne est cassée ? » a besoin de la ligne d'origine, pas de ta copie à moitié castée (glossary: quarantine). Sur un projet client, c'est rarement toi : l'équipe source possède le flux du fournisseur, donc la quarantine, c'est la table que tu lui remets.

3. Exercice : split core

Crée jobs/silver.py avec une fonction split(bronze_df) qui renvoie (good, rejected). good a ces colonnes, et aucune autre :

  • code, product_name, brands, categories, countries, nutrition_grade_fr : strings
  • sugars_100g : double
  • last_modified : date
  • loaded_at, pour le MERGE de cet après-midi

Pars de ce test, dans tests/test_silver.py :

import datetime as dt
from jobs.silver import split

COLS = "code string, product_name string, brands string, categories string, countries string, " \
       "nutrition_grade_fr string, sugars_100g string, last_modified string, loaded_at timestamp"
T0 = dt.datetime(2026, 10, 13, 14, 0)


def bronze(spark, *rows):
    return spark.createDataFrame([(c, n, "B", "Snacks", "France", "a", s, m, T0) for c, n, s, m in rows], COLS)


def test_each_rejected_row_names_its_rule(spark):
    good, rejected = split(bronze(spark,
        ("001", "ok",      "45",   "2026-03-01"),
        (None,  "nocode",  "1",    "2026-03-01"),
        ("003", "lots",    "lots", "2026-03-01"),
        ("004", "badDate", "1",    "March"),
        ("005", "nosugar", None,   "2026-03-01")))
    assert sorted((r.product_name, r.rule) for r in rejected.collect()) == [
        ("badDate", "last_modified_unparseable"),
        ("lots", "sugars_not_a_number"),
        ("nocode", "code_missing")]
    assert sorted((r.code, r.sugars_100g) for r in good.collect()) == [("001", 45.0), ("005", None)]

C'est bon quand le test passe et que dict(good.dtypes) montre double pour le sucre et date pour last_modified.

4. Exercice : la quarantine sur le drop 2 core

Ta vraie table bronze est sur GCS, et le Spark de ton laptop n'a pas de connecteur GCS. Du coup, tu vérifies avec un batch.

  1. Ajoute un __main__ à silver.py qui lit le bronze et le split.
  2. Écris le côté rejeté dans gs://…-silver/quarantine avec mode("overwrite").
  3. Affiche rejected.groupBy("rule").count().
  4. Déclare un batch silver dans Terraform comme celui du bronze : son propre silver_run, et en args le chemin du bronze, celui du silver et celui de la quarantine.

Pourquoi overwrite et pas append ? Parce que le silver lit tout le bronze à chaque run, donc chaque run recalcule tous les rejets. En append, une ligne du drop 2 apparaîtrait deux fois après deux runs. L'overwrite garde une ligne par rejet, et l'historique Delta garde toutes les versions précédentes (batch writes: overwrite).

C'est bon quand la sortie du batch montre un count par règle. Chaque ligne du drop 2 que tu as notée hier est dans ce count, ou alors tu sais expliquer pourquoi elle n'est pas fausse.

5. Stretch : toutes les règles, pas juste la première stretch

Une ligne sans code-barres et avec un sucre à "lots" ne prend que code_missing. Remplace la string rule par rules, un array de toutes les règles que la ligne rate :

  1. Construis un F.when(cond, name) par règle.
  2. Mets-les dans un F.array(...).
  3. Enlève les nulls avec F.array_compact. Une ligne est bonne quand l'array est vide.

Adapte ton test. Ensuite, dis dans la PR quelle version tu choisirais, et pourquoi. Laquelle est la plus simple pour la personne qui lit la quarantine ?
