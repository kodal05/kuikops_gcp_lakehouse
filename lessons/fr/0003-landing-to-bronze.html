Pourquoi cette leçon Les cinq gestes de ce matin deviennent le premier hop de ton pipeline. Même code, deux appelants : un test sur ton laptop (quelques secondes) et un batch sur GCS (quelques minutes). Une fois que ça marche, la gate te donne le drop 2. Et là, les ennuis du silver commencent.

1. Une fonction, deux appelants

Cette semaine, chaque hop est une fonction qui prend une session Spark et des chemins. Un bloc __main__ construit la session et lit les chemins dans sys.argv. Le test passe des dossiers temporaires, le batch passe des chemins de bucket. La fonction, elle, ne sait jamais lequel des deux l'appelle.

# learners/<handle>/jobs/bronze.py: the skeleton. You write the body.
import sys
from pyspark.sql import SparkSession, functions as F


def load_bronze(spark, landing, bronze):
    ...  # read every CSV under landing, stamp it, append it to the Delta table at bronze


if __name__ == "__main__":
    spark = (SparkSession.builder.appName("bronze")
             .config("spark.sql.extensions", "io.delta.sql.DeltaSparkSessionExtension")
             .config("spark.sql.catalog.spark_catalog", "org.apache.spark.sql.delta.catalog.DeltaCatalog")
             .getOrCreate())
    load_bronze(spark, sys.argv[1], sys.argv[2])
    print("bronze rows:", spark.read.format("delta").load(sys.argv[2]).count())

2. Exercice : le test d'abord core

Avant de coder, écris l'ordre que tu vas suivre : test, corps, batch, puis la gate (drop next, section 4). Puis démarre.

  1. Enregistre ça dans tests/test_bronze.py. Il utilise la fixture spark du template (conftest.py) et le tmp_path de pytest (pytest: temporary directories).
  2. Lance uv run pytest tests/test_bronze.py depuis learners/<handle>/ et regarde-le échouer.
  3. Remplis load_bronze avec les gestes 1 à 3 de la leçon 2 jusqu'à ce qu'il passe.
from jobs.bronze import load_bronze


def test_every_landed_row_is_stamped(spark, tmp_path):
    landing = tmp_path / "landing"; landing.mkdir()
    (landing / "a.csv").write_text("code,sugars_100g\n001,45\n002,0\n")
    (landing / "b.csv").write_text("code,sugars_100g\n001,44\n")

    load_bronze(spark, str(landing), str(tmp_path / "bronze"))

    b = spark.read.format("delta").load(str(tmp_path / "bronze"))
    got = sorted((r.code, r.sugars_100g, r.source_file.split("/")[-1])
                 for r in b.select("code", "sugars_100g", "source_file").collect())
    assert got == [("001", "44", "b.csv"), ("001", "45", "a.csv"), ("002", "0", "a.csv")]
    assert b.filter("loaded_at IS NULL").count() == 0

L'assertion compare des lignes, pas un count. Si le job perdait 001,44 et doublait 002, un count dirait quand même trois. Le 001 en double est normal : le bronze le garde.

C'est bon quand tu as 1 passed.

3. Exercice : la même fonction en batch core

Avec trois hops, le numéro de run unique de la leçon 1 relancerait les trois. Du coup, chaque hop a le sien. Le variables.tf du template a déjà bronze_run et drop. Mets leurs valeurs actuelles dans terraform.tfvars (il est commité). Sandbox : ici, c'est toi l'ordonnanceur. Sur un projet client, un orchestrateur soumet chaque hop dans cet ordre toutes les nuits. Quelqu'un est alerté quand l'un d'eux échoue (leçon 10, section 5).

resource "google_storage_bucket_object" "bronze_job" {
  bucket = google_storage_bucket.landing.name
  name   = "jobs/bronze.py"
  source = "${path.module}/../jobs/bronze.py"
}

resource "google_dataproc_batch" "bronze" {
  batch_id = "${var.handle}-bronze-${var.bronze_run}"
  location = "europe-west1"
  runtime_config {
    version    = "3.0"
    properties = { "spark.dynamicAllocation.maxExecutors" = "2" } # sandbox: drops are KBs, a client's GB a day needs executor sizing (lesson 10, section 5)
  }
  environment_config {
    execution_config {
      service_account = var.service_account
      ttl             = "1800s" # a hung batch is killed after 30 min
      authentication_config {
        user_workload_authentication_type = "SERVICE_ACCOUNT" # the API sets this: declare it or every apply replaces the batch
      }
    }
  }
  pyspark_batch {
    main_python_file_uri = "gs://${google_storage_bucket_object.bronze_job.bucket}/${google_storage_bucket_object.bronze_job.name}"
    args = [
      "gs://${google_storage_bucket.landing.name}/drop${var.drop}/",
      "gs://${google_storage_bucket.bronze.name}/products",
    ]
  }
}
# terraform.tfvars
drop       = 1
bronze_run = 1
terraform apply
gcloud dataproc batches wait <handle>-bronze-1 --region=europe-west1   # streams the driver output

batches wait affiche la sortie « pendant le run ou une fois qu'il est fini » (gcloud reference). C'est bon quand la sortie se termine par bronze rows: N, N étant le nombre de lignes de données du drop 1. Un batch qui a planté garde son id. Corrige le job, puis incrémente le numéro de run, sinon le prochain apply répond Error 409: Already exists.

Lance-le deux fois et le bronze double Refais un apply avec bronze_run = 2 et le même drop : chaque ligne du drop 1 est ajoutée une deuxième fois. C'est normal, c'est le bronze qui fait son boulot (il garde chaque chargement, avec son source_file et son loaded_at). Demain, le silver merge les copies en une seule ligne sur code. Mais du coup, tu ne relances que quand tu le veux vraiment. Change drop et bronze_run ensemble, et ne change jamais les args d'un batch sans nouveau numéro de run.

4. La gate, et le drop 2 core

drop next

La gate vérifie que chaque ligne du drop 1 est dans ta table bronze, avec un source_file et un loaded_at. Si elle refuse, son message dit ce qu'elle n'a pas trouvé. Quand elle passe :

  1. Le drop 2 arrive dans gs://kuikops-lakehouse-<handle>-landing/drop2/.
  2. Charge-le dans le bronze de la même façon (drop = 2, bronze_run = 3 ou le numéro suivant).
  3. Ouvre les fichiers et note trois trucs qui ont l'air faux. Ne les corrige pas : le bronze ne nettoie jamais, c'est le boulot de demain.

Refusé deux fois avec la même ligne ? Poste-la sur Teams avec ton handle, puis drop next --force. C'est tracé avec ton handle et l'heure, le formateur le voit, tu le dis dans ta PR, et gcloud storage rm -r gs://kuikops-lakehouse-<handle>-landing/drop2/ l'annule. Uniquement en sandbox : sur un projet client, rien ne te donne le fichier suivant, et un check qui échoue bloque le chargement jusqu'à ce que quelqu'un corrige la cause.

C'est bon quand le drop 2 est dans le bronze et que tu as noté trois trucs qui ont l'air faux.

5. La PR core

Sur la branche <handle>/bronze, commit jobs/bronze.py, tests/test_bronze.py et les changements Terraform. La CI lance tes tests et terraform validate. CI verte plus l'approbation de ton binôme, et c'est mergé. Ton binôme vérifie un truc en premier : est-ce que le job modifie une valeur qu'il a lue ? Si oui, cette ligne a sa place dans le silver.

6. Stretch : refuser un replay stretch

Fais en sorte que load_bronze saute les fichiers déjà présents dans le source_file du bronze. Comme ça, le même drop appliqué deux fois n'ajoute rien. Un join left_anti sur source_file contre la table fait le job (DataFrame.join). Le test d'abord : deux appels avec le même dossier donnent trois lignes, pas six. Ensuite, dis dans la PR si ça a sa place dans le bronze tout court. Un replay, c'est une erreur à empêcher ou un fait à enregistrer ?
