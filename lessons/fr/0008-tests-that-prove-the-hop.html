Des tests qui prouvent le hop, et la CI

Leçon 8 · jeudi 15h30 · Casse ton propre code exprès, regarde quel test le remarque, et laisse la CI le dire à tout le monde

≈ 75 minutesPrérequis : les tests de la leçon 5 qui passent, leçon 7 pas nécessaire avantRéférence : PySpark & Delta cheat sheet (en anglais) · glossaire (en anglais)
Pourquoi cette leçon Demain, le formateur lit toutes les PR. Comme un reviewer côté client, il ne lancera pas ton code. Il lira tes tests et le résultat de la CI. Un check vert ne veut dire quelque chose que si un hop faux le fait passer au rouge. Du coup aujourd'hui, c'est toi qui casses le hop.

1. Ce que la CI fait de ta PR

Le workflow du repo partagé (.github/workflows/) tourne sur chaque PR qui touche learners/<handle>/, uniquement dans ton dossier :

  • il lance uv run pytest et terraform validate
  • il ne lance jamais de batch, ne touche pas à GCS et ne fait pas de plan : il prouve le code, pas le cloud. Sur un projet client, un pipeline séparé avec ses propres credentials lance en général plan et apply, souvent dans un projet auquel tu n'as pas accès (leçon 10, section 5)
  • un check rouge bloque le merge

Quand c'est rouge :

  1. sur la PR, ouvre Checks et clique sur l'étape qui échoue
  2. cherche FAILED ou Error: dans le log. Le premier résultat donne le nom du test ou du fichier .tf
  3. ignore tout ce qui est au-dessus (les logs de setup)

2. Prédire, puis casser core

Une par une, fais chaque modification dans jobs/silver.py. Avant de lancer uv run pytest tests/test_silver.py, note quel test échoue, et avec quel message. Lance, compare, annule.

MutationChangement
AEnlève la condition : .whenMatchedUpdateAll() au lieu de .whenMatchedUpdateAll(condition="s.last_modified > t.last_modified")
BSaute la dédup : merge good.select(*SILVER_COLUMNS) au lieu de latest(good)

C'est bon quand tu as écrit une prédiction pour A et B, lancé les deux, et annulé les deux, avec uv run pytest tests/test_silver.py de nouveau vert.

Ce qu'on a vu — à ouvrir après les deux runs

A : test_latest_last_modified_wins_and_rerun_changes_nothing échoue sur sa première assertion, avec Old water et 2025-12-01 dans le silver. La mise à jour en retard a gagné.

B : le même test, mais la plupart des gens se trompent sur le message. Ce n'est pas DELTA_MULTIPLE_SOURCE_ROW…. Le premier MERGE écrit dans une table vide, du coup les trois lignes 001 sont insérées. Le test échoue sur une AssertionError avec des codes-barres en double (leçon 5). L'erreur du MERGE n'apparaîtrait qu'au deuxième run. Un test qui compare des lignes le voit dès le premier.

Un test qui vérifie silver.count() == 2 serait passé avec la mutation A. C'est pour ça qu'on compare des lignes.

3. Exercice : fais tourner le hop entier deux fois core

Jusqu'ici chaque test vérifie une fonction. Celui-ci fait tourner un hop entier via run, deux fois, comme le batch. Il vérifie ta règle la plus importante : une ligne sans code-barres n'arrive jamais dans le silver et atterrit en quarantine une seule fois. Dans tests/test_run.py, il te faut :

  • un dossier landing dans tmp_path avec un CSV, les huit colonnes : une bonne ligne, une avec un code vide
  • load_bronze, puis silver.run(spark, bronze, silver, quarantine) deux fois
  • deux assertions sur les lignes : les codes du silver sont ["001"], et la quarantine contient une seule paire (product_name, rule)

Ensuite commente la règle code_missing et relance. S'il passe toujours, il ne teste pas ce que tu crois.

C'est bon quand le test passe, échoue sans la règle, et repasse quand la règle revient.

4. Exercice : rouge, puis vert, dans la CI core

Crée la branche <handle>/tests, puis :

  1. Premier commit : le nouveau test et la mutation A. Push, ouvre une PR en draft, et trouve le test qui échoue dans le log de la CI (la recherche de la section 1).
  2. Deuxième commit : annule la mutation. Push et regarde-la passer au vert.
  3. Passe la PR en ready et demande une review à ton binôme. Dans la description, colle la ligne rouge du log qui a nommé le problème.

C'est bon quand la PR montre un run rouge et un run vert, et qu'elle est mergée.

5. Stretch : tout le pipeline dans un seul test stretch

Écris test_pipeline.py avec deux dossiers de drop : un doublon, une mise à jour en retard, un code-barres null, un "12 g". Lance bronze, silver et gold dans l'ordre, puis fais une assertion sur les lignes de chaque table gold. C'est ton test le plus lent, donc garde-en un seul. Il répond au « est-ce que ça marche de bout en bout ? » d'un reviewer.
