Delta's history, restore, and drop 4

Lesson 7 · Thursday 13:15 · Ask a table what a hop did, undo a bad run, and choose to accept a schema change

≈ 2 hoursPrerequisite: lesson 6, drop 3 through goldReference: PySpark & Delta cheat sheet · glossary
Why this lesson Every real platform asks two questions, usually at a bad moment: "what did last night's run change?" and "can we put it back?". Delta's log answers both. Then drop 4 brings the renamed and new columns from lesson 2's war story, and this time you accept them by choice.

1. The log is the table's memory

Each successful write is a commit with a version, an operation and metrics (table utility commands). For a MERGE:

h = DeltaTable.forPath(spark, silver).history()
h.select("version", "operation",
         F.col("operationMetrics.numTargetRowsInserted").alias("ins"),
         F.col("operationMetrics.numTargetRowsUpdated").alias("upd")).orderBy("version").show()

Here's silver after you build it twice from the same bronze. History comes newest-first, that's why you add orderBy:

versionoperationinsupdReading
0WRITENULLNULLempty table from your first run
1MERGE60first load: six barcodes, all new
2MERGE00re-run, same bronze: nothing changed

To go back in the log:

  • spark.read.format("delta").option("versionAsOf", n) reads the table as it was at version n.
  • DeltaTable.forPath(spark, path).restoreToVersion(n) makes version n current again, as a new commit (RESTORE in history). Nothing gets erased.

2. Exercise: break it, see it, restore it core

Locally, in jobs/explore_history.py, build silver with your own split and merge_silver from four or five bronze rows. Then fake a bad run from a wrong mode:

v_good = DeltaTable.forPath(spark, silver).history(1).first().version
spark.read.format("delta").load(silver).limit(1) \
     .write.format("delta").mode("overwrite").save(silver)        # the bad run

Predict each step in writing, then print:

  1. the current row count
  2. the row count at versionAsOf = v_good
  3. the last three history entries (version, operation)
  4. after restoreToVersion(v_good): the row count, and the last operation.

Done when the restored count equals the count at v_good, history ends with RESTORE, and you can explain why the bad version is still readable.

Restore has a limit Time travel and restore need the old data files. Once VACUUM deletes unreferenced files past retention (7 days by default), those versions are gone (utility commands: vacuum). Nobody runs VACUUM this week. On a client platform, ask who does, and when.

3. Drop 4: predict first

Drop 4's header renames sugars_100g to sugar_100g and adds ecoscore_grade. Your bronze job appends whatever it reads. What happens? Write it down, then check lesson 2's move 5.

What happens — open after you predicted

The batch fails: A schema mismatch detected when writing to the Delta table. Bronze refuses the two unknown columns, sugar_100g and ecoscore_grade, and writes nothing. That error is the guard that the platform in lesson 2's war story had switched off.

The guard misses one case: a drop that's just missing a column goes through, with that column null in every row. If the supplier had removed sugars_100g, bronze would have loaded it with no error, and silver would have lost sugar. Missing columns are a job for your contract and your rule counts.

4. Exercise: accept the change, on purpose core

Two decisions, each one line a reviewer can read in your PR:

from delta import DeltaTable

RENAMES = {"sugar_100g": "sugars_100g"}   # drop 4: the supplier renamed a column
ADDED = {"ecoscore_grade": "STRING"}      # drop 4: a new column, accepted on purpose


def load_bronze(spark, landing, bronze):
    raw = spark.read.option("header", True).csv(landing).withColumnsRenamed(RENAMES)
    if DeltaTable.isDeltaTable(spark, bronze):
        have = set(spark.read.format("delta").load(bronze).columns)
        for name, sql_type in ADDED.items():
            if name in raw.columns and name not in have:
                spark.sql(f"ALTER TABLE delta.`{bronze}` ADD COLUMNS ({name} {sql_type})")
    ...  # stamp and append, unchanged

withColumnsRenamed ignores missing names, so older drops go through untouched (API). ALTER TABLE … ADD COLUMNS commits on its own: history shows the decision, and older rows read null (batch writes: update table schema). Write both tests first:

def test_drop4_rename_and_new_column(spark, tmp_path):
    for n, body in [("drop1", "code,sugars_100g\n001,45\n"),
                    ("drop4", "code,sugar_100g,ecoscore_grade\n002,4,a\n")]:
        (tmp_path / n).mkdir(); (tmp_path / n / "p.csv").write_text(body)
        load_bronze(spark, str(tmp_path / n), str(tmp_path / "bronze"))
    b = spark.read.format("delta").load(str(tmp_path / "bronze"))
    assert sorted((r.code, r.sugars_100g, r.ecoscore_grade) for r in b.collect()) == [
        ("001", "45", None), ("002", "4", "a")]


def test_unknown_new_column_is_refused(spark, tmp_path):
    import pytest
    for n, body in [("d1", "code\n001\n"), ("d2", "code,surprise\n002,x\n")]:
        (tmp_path / n).mkdir(); (tmp_path / n / "p.csv").write_text(body)
    load_bronze(spark, str(tmp_path / "d1"), str(tmp_path / "bronze"))
    with pytest.raises(Exception, match="schema mismatch"):
        load_bronze(spark, str(tmp_path / "d2"), str(tmp_path / "bronze"))

The second test keeps the guard: the next surprise column still fails. Then load drop 4 into bronze and re-run silver and gold. One catch: silver overwrites quarantine, and the rejected rows now carry ecoscore_grade, so the same guard refuses that write. Quarantine is rebuilt every run, so let its schema follow bronze: add .option("overwriteSchema", "true") to the quarantine write. Read each batch with gcloud dataproc batches wait (lesson 3, section 3), last Traceback first if it failed. ecoscore_grade stays out of silver until someone decides it should.

Done when both tests pass, drop 4 is in bronze, and bronze's history shows ADD COLUMNS. drop next checks drop 4 and hands you drop 5, Friday's capstone. Starting it is up to you.

5. Stretch: which rows changed stretch

To see which rows changed, not how many, diff silver's last two versions: print new.exceptAll(old) and old.exceptAll(new) (exceptAll). Add it to the silver batch's output after the MERGE, capped at 20 rows. On a client platform, that's the snippet for the incident channel.
