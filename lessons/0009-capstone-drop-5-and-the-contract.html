Capstone: drop 5 and the contract

Lesson 9 · Friday 09:50 · Run the whole pipeline on the worst drop, and let a contract tell you if silver is right

Build 09:50 to 12:15Prerequisite: drop 4 in bronze (lesson 7)Reference: silver contract · PySpark & Delta cheat sheet · glossary
Why this lesson On a client project, you don't get to say "silver is right". A check says it for you. This morning a data contract checks your silver, and passing it on drop 5 is the week's pass criterion. Every line is a rule you built on Wednesday or Thursday, only now a tool checks it.

1. Read the contract

Open reference/silver-contract.odcs.yaml. It's in the Open Data Contract Standard (ODCS), a YAML format for "what a table promises". Three lines cover the week:

Contract lineWhat it checksWhich work makes it pass
code: required, uniqueno null barcode, no barcode twicecode_missing rule, plus latest + MERGE (lesson 5)
last_modified: required, dateevery row has a parsed datetwo date formats, unparseable → quarantine (lessons 4 and 6)
sugars_100g: number, minimum 0, maximum 100no impossible sugar valuetoday

It also checks the eight silver columns and their types. drop check silver registers your silver as silver_food_products and runs the contract with datacontract-cli. Each check prints [passed] or [failed] with a reason:

[failed] Check that field sugars_100g has a maximum of 100 -- Actual invalid_count(sugars_100g) was 1, expected = 0

2. Predict drop 5 before you load it

Drop 5 keeps the defects of drops 2 to 4. It adds two new ones: sugar values outside 0 to 100, and a file cut off in the middle of a row. With your pipeline as it is, write down where each ends up (bronze? silver? quarantine, under which rule?). Does the contract pass?

What happens — open once you've run drop 5

Out-of-range sugar: "120" casts to 120.0 with no error. No rule fires, so it lands in silver and the contract fails on the maximum. A value can be well-formed and impossible.

The cut-off row: the CSV reader fills the missing trailing fields with null. So the row reaches bronze with no last_modified. Silver quarantines it as last_modified_unparseable, a rule written for something else. Check its count: a rule that fires for two reasons hides one.

3. Exercise: the last rule core

  1. Add a row to your split test: ("009", "toomuch", "120", "2026-03-01"), expected in quarantine as sugars_out_of_range.
  2. Add the rule to the F.when chain, after sugars_not_a_number, on the typed value: (F.col("_sugars") < 0) | (F.col("_sugars") > 100).

A null sugar means unknown, not out of range. Check that your rule agrees.

Done when the test passes and your 005 row with no sugar stays in silver.

4. Exercise: end to end, then the check core

  1. drop next (if you don't have drop 5 yet).
  2. Bronze: drop = 5, bump bronze_run, apply, batches wait.
  3. Silver: bump silver_run, apply, wait. Read the rule counts first.
  4. Gold: bump gold_run, apply, wait.
  5. drop check silver, until every line says [passed].

One apply per hop, each waiting for the last: Terraform starts all batches of one apply side by side, and silver needs bronze finished. Sandbox: here you're the scheduler. On a client project an orchestrator submits each hop in this order every night. Someone gets paged when one fails (lesson 10, section 5).

Done when drop check silver is all green on drop 5 (the pass criterion).

5. The capstone PR core

Make a branch <handle>/capstone with everything since your last merge. In the description, paste:

  • the rule counts from the drop-5 silver run
  • the last line of drop check silver
  • one sentence on what changes in your pipeline, and in which layer, if the client says suppliers will now resend corrected rows with an unchanged last_modified
  • the output of terraform state list, showing your four buckets and the bronze, silver and gold batches

Then pair review, green CI, and the instructor's review, which is required on this PR.
