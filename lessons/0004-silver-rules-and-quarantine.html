Silver's rules and quarantine

Why this lesson On Friday a contract checks silver: typed columns, a barcode and a valid date on every row. Today you write the half of silver that makes that possible. It types bronze's strings, then splits the rows in two: the ones silver keeps, and the ones it refuses, each labelled with its rule. This afternoon's MERGE only sees the good side.

1. Predict, then run

Bronze is all strings. Silver casts, and a cast that can't succeed raises instead of returning null: ANSI mode is on by default (migration guide). Predict each line, then run it in a local session with spark.sql(f"SELECT {e}").first()[0]:

ExpressionYour prediction
cast('12 g' AS double)
try_cast('12 g' AS double)
to_date('15/03/2026', 'yyyy-MM-dd')
try_to_timestamp('15/03/2026', 'yyyy-MM-dd')
What we saw — open after you ran them

Line 1 raises [CAST_INVALID_INPUT] The value '12 g' of the type "STRING" cannot be cast to "DOUBLE" because it is malformed. Line 3 raises [CANNOT_PARSE_TIMESTAMP]. Lines 2 and 4 return None.

So with lines 1 and 3, one bad row kills the whole batch. With the try_ forms, the row survives as a null that a rule can catch. That's why silver only uses those (pyspark.sql.functions: try_to_timestamp, and try_cast through F.expr).

2. One rule column

A rule is a condition plus a name, chained in one F.when. A row's rule column holds the first rule it fails, or null if it fails none. So filtering on that one column gives both sides, and no row falls between them.

sugars   = F.expr("try_cast(sugars_100g AS double)")
modified = F.to_date(F.try_to_timestamp("last_modified", F.lit("yyyy-MM-dd")))
typed = bronze_df.withColumns({"_sugars": sugars, "_modified": modified})

rule = (F.when(F.col("code").isNull() | (F.trim("code") == ""), "code_missing")
         .when(F.col("_modified").isNull(), "last_modified_unparseable")
         .when(F.col("sugars_100g").isNotNull() & F.col("_sugars").isNull(), "sugars_not_a_number"))
judged = typed.withColumn("rule", rule)

Watch the third rule. Missing sugar is unknown, not an error, so silver keeps it as null. Sugar that was there but couldn't be read is an error. The isNotNull() on the bronze column makes the difference.

What quarantine holds The rejected row exactly as bronze had it (all strings, with source_file and loaded_at), plus rule and rejected_at. Whoever asks the supplier "why is this row broken?" needs the original row, not your partly cast copy (glossary: quarantine). On a client project that's rarely you: the source team owns the supplier feed, so quarantine is the table you hand them.

3. Exercise: split core

Create jobs/silver.py with split(bronze_df) returning (good, rejected). good has these columns, and no others:

  • code, product_name, brands, categories, countries, nutrition_grade_fr: strings
  • sugars_100g: double
  • last_modified: date
  • loaded_at, for this afternoon's MERGE

Start from this test, in tests/test_silver.py:

import datetime as dt
from jobs.silver import split

COLS = "code string, product_name string, brands string, categories string, countries string, " \
       "nutrition_grade_fr string, sugars_100g string, last_modified string, loaded_at timestamp"
T0 = dt.datetime(2026, 10, 13, 14, 0)


def bronze(spark, *rows):
    return spark.createDataFrame([(c, n, "B", "Snacks", "France", "a", s, m, T0) for c, n, s, m in rows], COLS)


def test_each_rejected_row_names_its_rule(spark):
    good, rejected = split(bronze(spark,
        ("001", "ok",      "45",   "2026-03-01"),
        (None,  "nocode",  "1",    "2026-03-01"),
        ("003", "lots",    "lots", "2026-03-01"),
        ("004", "badDate", "1",    "March"),
        ("005", "nosugar", None,   "2026-03-01")))
    assert sorted((r.product_name, r.rule) for r in rejected.collect()) == [
        ("badDate", "last_modified_unparseable"),
        ("lots", "sugars_not_a_number"),
        ("nocode", "code_missing")]
    assert sorted((r.code, r.sugars_100g) for r in good.collect()) == [("001", 45.0), ("005", None)]

Done when the test passes and dict(good.dtypes) shows double for sugars and date for last_modified.

4. Exercise: quarantine on drop 2 core

Your real bronze table is on GCS, and your laptop's Spark has no GCS connector, so you check it with a batch.

  1. Add a __main__ to silver.py that reads bronze and splits it.
  2. Write the rejected side to gs://…-silver/quarantine with mode("overwrite").
  3. Print rejected.groupBy("rule").count().
  4. Declare a silver batch in Terraform like bronze's: its own silver_run, and args bronze path, silver path, quarantine path.

Why overwrite and not append? Silver reads all of bronze every run, so each run recomputes every rejection. Appending would list a drop-2 row twice after two runs. Overwrite keeps one row per rejection, and Delta's history keeps every earlier version (batch writes: overwrite).

Done when the batch output shows a count per rule. Each drop-2 row you flagged yesterday is in that count, or you can say why it isn't wrong.

5. Stretch: every rule, not the first stretch

A row with no barcode and sugar "lots" only gets code_missing. Replace the rule string with rules, an array of every rule the row fails:

  1. Build one F.when(cond, name) per rule.
  2. Wrap them in F.array(...).
  3. Remove the nulls with F.array_compact. A row is good when the array is empty.

Adjust your test. Then say in the PR which version you'd pick, and why: which is easier for whoever reads quarantine?
