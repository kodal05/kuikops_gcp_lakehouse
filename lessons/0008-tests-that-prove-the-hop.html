Tests that prove the hop, and CI

Lesson 8 · Thursday 15:30 · Break your own code on purpose, see which test notices, and let CI tell everyone

≈ 75 minutesPrerequisite: lesson 5 tests passing, lesson 7 not needed firstReference: PySpark & Delta cheat sheet · glossary
Why this lesson Tomorrow the instructor reads every PR. Like a client reviewer, they won't run your code, they'll read your tests and the CI result. A green tick only means something if a wrong hop turns it red. So today you break the hop yourself.

1. What CI does with your PR

The shared repo's workflow (.github/workflows/) runs on every PR touching learners/<handle>/, only in your folder:

  • it runs uv run pytest and terraform validate
  • it never runs a batch, touches GCS or plans: it proves the code, not the cloud. On a client project a separate pipeline with its own credentials usually runs plan and apply, often in a project you can't touch (lesson 10, section 5)
  • a red check blocks the merge

When it's red:

  1. on the PR, open Checks and click the failing step
  2. search the log for FAILED or Error:. The first match names the test or the .tf file
  3. skip everything above it (setup logs)

2. Predict, then break core

One at a time, make each change in jobs/silver.py. Before running uv run pytest tests/test_silver.py, write down which test fails, and its message. Run, compare, undo.

MutationChange
ARemove the condition: .whenMatchedUpdateAll() instead of .whenMatchedUpdateAll(condition="s.last_modified > t.last_modified")
BSkip the dedup: merge good.select(*SILVER_COLUMNS) instead of latest(good)

Done when you've written a prediction for A and B, run both, and undone both, with uv run pytest tests/test_silver.py green again.

What we saw — open after both runs

A: test_latest_last_modified_wins_and_rerun_changes_nothing fails on its first assertion, with Old water and 2025-12-01 in silver. The late update won.

B: the same test, but most people guess the wrong message. It's not DELTA_MULTIPLE_SOURCE_ROW…. The first MERGE goes into an empty table, so all three 001 rows get inserted. The test fails on an AssertionError with duplicate barcodes (lesson 5). The MERGE error would only show on the second run. A test comparing rows catches it on the first.

A test asserting silver.count() == 2 would have passed mutation A. That's why you compare rows.

3. Exercise: run the whole hop twice core

So far each test checks one function. This one runs a whole hop through run, twice, like the batch. It checks your most important rule: a row without a barcode never reaches silver and lands in quarantine exactly once. In tests/test_run.py, you need:

  • a landing folder in tmp_path with one CSV, all eight columns: one good row, one with an empty code
  • load_bronze, then silver.run(spark, bronze, silver, quarantine) twice
  • two assertions on rows: silver's codes are ["001"], and quarantine has a single (product_name, rule) pair

Then comment out the code_missing rule and run it. If it still passes, it's not testing what you think.

Done when the test passes, fails without the rule, and passes again with the rule back.

4. Exercise: red, then green, in CI core

Branch <handle>/tests, then:

  1. First commit: the new test and mutation A. Push, open a draft PR, and find the failing test in the CI log (section 1's search).
  2. Second commit: undo the mutation. Push and watch it go green.
  3. Mark the PR ready and ask your pair to review. In the description, paste the red log line that named the problem.

Done when the PR shows one red and one green run, and is merged.

5. Stretch: the whole pipeline in one test stretch

Write test_pipeline.py with two drop folders: a duplicate, a late update, a null barcode, a "12 g". Run bronze, silver and gold in order, then assert on each gold table's rows. It's your slowest test, so keep just one. It answers a reviewer's "does it work end to end?"
