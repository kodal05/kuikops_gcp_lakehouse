1. One function, two callers

Every hop this week is a function that takes a Spark session and paths. A __main__ block builds the session and reads the paths from sys.argv. The test passes temp folders, the batch passes bucket paths, and the function never knows which.

# learners/<handle>/jobs/bronze.py: the skeleton. You write the body.
import sys
from pyspark.sql import SparkSession, functions as F


def load_bronze(spark, landing, bronze):
    ...  # read every CSV under landing, stamp it, append it to the Delta table at bronze


if __name__ == "__main__":
    spark = (SparkSession.builder.appName("bronze")
             .config("spark.sql.extensions", "io.delta.sql.DeltaSparkSessionExtension")
             .config("spark.sql.catalog.spark_catalog", "org.apache.spark.sql.delta.catalog.DeltaCatalog")
             .getOrCreate())
    load_bronze(spark, sys.argv[1], sys.argv[2])
    print("bronze rows:", spark.read.format("delta").load(sys.argv[2]).count())

2. Exercise: the test first core

Before you code, write the order you'll go in: test, body, batch, then the gate (drop next, section 4). Then start.

  1. Save this as tests/test_bronze.py. It uses the template's spark fixture (conftest.py) and pytest's tmp_path (pytest: temporary directories).
  2. Run uv run pytest tests/test_bronze.py from learners/<handle>/ and watch it fail.
  3. Fill in load_bronze with lesson 2's moves 1 to 3 until it passes.
from jobs.bronze import load_bronze


def test_every_landed_row_is_stamped(spark, tmp_path):
    landing = tmp_path / "landing"; landing.mkdir()
    (landing / "a.csv").write_text("code,sugars_100g\n001,45\n002,0\n")
    (landing / "b.csv").write_text("code,sugars_100g\n001,44\n")

    load_bronze(spark, str(landing), str(tmp_path / "bronze"))

    b = spark.read.format("delta").load(str(tmp_path / "bronze"))
    got = sorted((r.code, r.sugars_100g, r.source_file.split("/")[-1])
                 for r in b.select("code", "sugars_100g", "source_file").collect())
    assert got == [("001", "44", "b.csv"), ("001", "45", "a.csv"), ("002", "0", "a.csv")]
    assert b.filter("loaded_at IS NULL").count() == 0

The assertion compares rows, not a count. If the job lost 001,44 and doubled 002, a count would still say three. The duplicate 001 is expected: bronze keeps it.

Done when 1 passed.

3. Exercise: the same function as a batch core

With three hops, lesson 1's single run number would re-run all of them, so each hop gets its own. The template's variables.tf already has bronze_run and drop. Set their current values in terraform.tfvars (it's committed). Sandbox: here you're the scheduler. On a client project an orchestrator submits each hop in this order every night. Someone gets paged when one fails (lesson 10, section 5).

resource "google_storage_bucket_object" "bronze_job" {
  bucket = google_storage_bucket.landing.name
  name   = "jobs/bronze.py"
  source = "${path.module}/../jobs/bronze.py"
}

resource "google_dataproc_batch" "bronze" {
  batch_id = "${var.handle}-bronze-${var.bronze_run}"
  location = "europe-west1"
  runtime_config {
    version    = "3.0"
    properties = { "spark.dynamicAllocation.maxExecutors" = "2" } # sandbox: drops are KBs, a client's GB a day needs executor sizing (lesson 10, section 5)
  }
  environment_config {
    execution_config {
      service_account = var.service_account
      ttl             = "1800s" # a hung batch is killed after 30 min
      authentication_config {
        user_workload_authentication_type = "SERVICE_ACCOUNT" # the API sets this: declare it or every apply replaces the batch
      }
    }
  }
  pyspark_batch {
    main_python_file_uri = "gs://${google_storage_bucket_object.bronze_job.bucket}/${google_storage_bucket_object.bronze_job.name}"
    args = [
      "gs://${google_storage_bucket.landing.name}/drop${var.drop}/",
      "gs://${google_storage_bucket.bronze.name}/products",
    ]
  }
}
# terraform.tfvars
drop       = 1
bronze_run = 1
terraform apply
gcloud dataproc batches wait <handle>-bronze-1 --region=europe-west1   # streams the driver output

batches wait shows the output "as it runs or after it completes" (gcloud reference). Done when the output ends with bronze rows: N, N being the data lines in drop 1. A failed batch keeps its id. Fix the job, then bump the run number, or the next apply answers Error 409: Already exists.

Run it twice and bronze doubles Apply again with bronze_run = 2 and the same drop: every row of drop 1 is appended again. That's bronze doing its job (it keeps every load, with its source_file and loaded_at), and tomorrow silver merges the copies into one row on code. So only re-run when you mean it. Change drop and bronze_run together, and never change a batch's args without a new run number.

4. The gate, and drop 2 core

drop next

The gate checks that every row of drop 1 is in your bronze table, with a source_file and a loaded_at. If it refuses, its message names what it couldn't find. When it passes:

  1. Drop 2 lands in gs://kuikops-lakehouse-<handle>-landing/drop2/.
  2. Load it into bronze the same way (drop = 2, bronze_run = 3 or whatever's next).
  3. Open the files and write down three things that look wrong. Don't fix them: bronze never cleans, that's tomorrow's work.

Refused twice with the same line? Post it in Teams with your handle, then drop next --force. It's logged with your handle and the time, the instructor sees it, you name it in your PR, and gcloud storage rm -r gs://kuikops-lakehouse-<handle>-landing/drop2/ undoes it. Sandbox only: on a client project nothing hands you the next file, and a check that fails stops the load until someone fixes the cause.

Done when drop 2 is in bronze and you've written down three things that look wrong.

5. The PR core

On the branch <handle>/bronze, commit jobs/bronze.py, tests/test_bronze.py and the Terraform changes. CI runs your tests and terraform validate, and green CI plus your pair's approval merges it. Your pair checks one thing first: does the job change any value it read? If yes, that line belongs in silver.

6. Stretch: refuse a replay stretch

Make load_bronze skip files already in bronze's source_file, so the same drop applied twice appends nothing. A left_anti join on source_file against the table does it (DataFrame.join). Test first: two calls with the same folder give three rows, not six. Then say in the PR whether this belongs in bronze at all: is a replay a mistake to prevent, or a fact to record?
